Both bugs are the same Go-reflection mistake: treating reflect.Kind as if it equals reflect.Type. It doesn't.

  The setup. Protobuf generates enums as named int32 aliases:
  type PhysioJoint int32
  type PhysioExerciseCategory int32
  For reflection, PhysioJoint has Kind() == reflect.Int32 (same primitive category as plain int32), but its Type() is physio.PhysioJoint, not int32. reflect.Value.Set requires type assignability, not kind
  equality — so you can't shove a plain int32 into a PhysioJoint slot.

  The trigger. Commit 9826957 added two new repeated-enum fields on PhysioExercise:
  Joints     []PhysioJoint
  Categories []PhysioExerciseCategory
  These are the first slice-of-named-enum fields the system has seen. Singular fields like Joint PhysioJoint already existed and worked because the existing code had a one-off hack for that exact case — but only
   for the singular case, and only at the struct field level.

  Bug 1 — l8reflect deep cloner. The cloner dispatches by Kind(). When it cloned a PhysioJoint element, it ran the generic int32Cloner, which returns reflect.ValueOf(int32(i)) — losing the named type.
  structCloner had a workaround (if cloned.Kind() == reflect.Int32 { SetInt(...) }) that papered over this for struct fields, but sliceCloner, arrayCloner, and mapCloner had no such guard. So cloning a
  []PhysioJoint panicked the first time it tried to Set a plain int32 into a PhysioJoint slot. The fix: in those three cloners, if the cloned element's type doesn't match the destination's, Convert it first
  (handles all named numeric aliases, not just int32).

  Bug 2 — l8orm Postgres reader. When decoding a packed-enum column, the byte decoder produces a []int32. SetValueFromRow then checked fieldValue.Kind() == setFieldValue.Kind() — both are reflect.Slice, so it
  called Set. But Set rejected it: []int32 is not assignable to []PhysioExerciseCategory, even though their elements have the same underlying type. (Go doesn't allow direct conversion between two slice types
  with different named element types either, so a single Convert on the slice doesn't work — you have to rebuild the slice element by element.) The fix: when kinds match but the slice element types differ and
  are convertible, allocate a fresh slice of the destination type and convert each element.

  Why patch the libraries, not the model. The type-loss happens inside reflection-driven generic code in those libraries. The only alternatives in l8physio would be (a) stop using protobuf enums for repeated
  fields — gives up type safety in the schema, or (b) hand-roll custom marshallers per model — defeats the purpose of using l8reflect/l8orm. The fix has to live where the reflection code lives. And it's a real
  bug for any other consumer that adds a slice-of-named-enum field, not l8physio-specific.
